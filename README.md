# superagent-mini

一个**常驻的超级 Agent**：在飞书里说一句"帮我看看这个文件"，Router 判断要不要干活，
Worker 在隔离会话里真去干，结论回到飞书。事件驱动、并发、可恢复、有留痕。

不是框架，不是产品，是一个**能跑起来的架构验证**：把 DeepSeek Harness 团队那篇
Super-agent 架构文章里的判断，一条一条落到代码上，然后**用实测数字检验它们**。
做的时候是净室实现——只看文章，不看官方原型；跑出数之后才去读他们的代码，逐条对照在 [`docs/COMPARE.md`](docs/COMPARE.md)。

```
事件（飞书消息 / CI 结果 / PR 评论）
   │
   ▼
Supervisor  ── 唯一常驻的东西。只做确定性的事：拉事件、过滤、路由、调度、落盘
   │
   ├─ Fast Path（代码，不花钱）：机器人自己的消息、配置里明确不理的 → 直接丢
   │
   ├─ 有订阅者？ ──是──→ 直通 Worker（不过模型）
   │
   └─ 没有 ──→ Router（一个 DSH 会话，无执行工具）
                  │  一轮一批，只调一次模型（批处理）
                  │  只能说三种话：dispatch / ignore / reply_only
                  ▼
              Worker（每个任务一个 DSH 会话，独立工作目录与能力集）
                  │  长任务不阻塞 supervisor
                  ▼
              汇报 → 回队成一条 Trigger → 过 Router → 一句话回给用户
```

## 四组实测数字

合成负载：20 条工作请求（分 4 个 Thread）+ 200 条噪音，工作 = 3 次 `sleep(200ms)`。
复现：`node src/harness.ts`（约 4 分钟）。

| 方案 | p50 | p95 | Router 决策 | 模型调用 | 直通 | token | 总耗时 |
|---|---|---|---|---|---|---|---|
| A 单会话串行 | 827ms | 839ms | 220 | 220 | 0 | 267,920 | 182.2s |
| B 双层 + 直通 | 633ms | 3237ms | **7** | **7** | 193 | 269,953 | **5.5s** |
| C 双层无直通 | 638ms | 34,506ms | 200 | 200 | 0 | 273,620 | 44.9s |

**B vs C：决策 200 → 7，总时长 44.9s → 5.5s。** 收益与"重复事件占比"成正比——
我们是 200 噪音 : 20 工作，所以是 28 倍，而文章消融实验说的是 +30%。
**不能引用文章的数字，只能引用自己负载下的数字**，这是做基准的第一条纪律。

**A 的 p95 比 B 好（839ms vs 3237ms）**，这不是 bug 是取舍：双层的 Router 是全局序点，
它慢全局慢。要压 p95 得让 Router 更快、或在主循环里更早批处理。

## 接上真东西之后，四个数字变了

合成负载里的 Worker 是假 sleep，下面这些问题一个都不会暴露。它们是真接上飞书和真 DSH 之后撞出来的：

| 问题 | 改之前 | 改之后 |
|---|---|---|
| 同步 IO 把并发吃掉了（`execFileSync`） | `+ Worker` 到下一句回话 **182 秒** | **3 秒** |
| Worker 继承了 7 个不相关插件 | 同一任务 **20 秒超时** | **7.8 秒**，结论还对 |
| Worker 宁可耗死也不说"没找到" | **120 秒超时**，什么都没说 | **14.6 秒**，诚实报告 |
| 空闲判定用错口径（轮询源天生重复投递） | 忙轮询，定时器饿死，Worker 汇报永远等不到 | 用"去重后的新事件数"判空闲 |

**这四个数字比上面那张基准表更值钱**，因为它们抄不走：要得到它们，必须先正确地撞墙。
七个坑的完整记录（含根因和修法）在 [`docs/RESULTS.md`](docs/RESULTS.md)。

## 跑起来

要求 **Node 24+**（用了 `.ts` 直接执行和顶层 `await`）。下面用 `npm`；仓库里也有 `pnpm-lock.yaml`，用 pnpm 的话把命令里的 `npm` 换成 `pnpm` 即可。

```bash
npm test                  # 44 个用例，不需要任何外部服务
node src/harness.ts       # 合成负载基准，约 4 分钟，出上面那张表
```

**接真模型（不需要飞书）**：一句话进去，Router 判断，Worker 真干活，回一句话出来。
`src/dsh.ts` 会优先用项目内的 `@deepseek-ai/dsh`，找不到才退回开发目录并打印警告。

```bash
npm i
node src/demo.ts "看看 src/filter.ts 里空 actor 有没有边界问题"
```

**接真飞书（常驻）**：需要一个飞书自建应用 + 把机器人拉进群。配置全走环境变量：

```bash
export SAM_CHAT_ID=oc_xxxxxxxxxxxx        # 必填，要盯的群
export SAM_STATE_DIR=/var/lib/superagent  # 状态目录，默认 ./state
# 可选：SAM_LARK_BIN / SAM_DSH_BIN / SAM_DSH_HOME / SAM_INTERVAL_MS
node src/run.ts
```

首次启动会画一条水位线：**只处理此刻之后的消息**，群里的历史不回溯——
不然第一次跑就会对着半年前的"哈喽在吗"派 Worker。想回放历史用 `FEISHU_SINCE`：

```bash
FEISHU_SINCE=2026-10-29T14:57:00.000Z DSH_WORKER_TIMEOUT_MS=20000 \
  SAM_CHAT_ID=oc_xxx node src/run.ts
```

部署到一台 Linux 机器（systemd / 权限 / 密钥）见 [`docs/DEPLOY.md`](docs/DEPLOY.md)。

## 设计里几个不显然的选择

**Router 没有执行工具。** 它的 profile 里就没有 bash。用 profile 差异实现"Router 不能干活"，
而不是靠提示词求它别干。

**汇报绝不直通。** Worker 的汇报和原任务同一个 `threadKey`，而那个 Thread 的订阅者正是
**发出汇报的那个 Worker**——直通会把汇报投回它自己，形成自激循环。
所以 `source === 'worker'` 的 Trigger 一律过 Router。**死循环在路由层，不在模型层，
所以规则写在代码里，不是写在提示词里。**

**空汇报也算结论。** Worker 什么都没说，这件事必须回队并告诉用户。
原来的 `if (text.length === 0) return` 会让任务静默蒸发——用户永远等不到第二句话。

**Worker 的执行纪律随任务一起下发。** 找不到目标就停下、说清查过哪里、
**绝不为交差造一个替代实现**。最后这条是因为"造一个替代实现"是最坏的失败形态：
它有产出，看起来像干成了。

**出门那句话的形状由代码保证，不靠提示词。** 模型说什么是一件事，发到群里长什么样是另一件事：
剥内部信封（`[worker] w-ab12cd34: `）、压平空白、超过 400 字截断并把全文存档。
提示词里也写了"简短"，但那是一次建议；`src/channel.ts` 是拒绝。两件事都要有。

**实现细节不进模型的输入。** 失败时抛的是 `dsh headless 超时（20000ms）：worker-w-…`，
原样喂给 Router 让它"转述"，转出来必然是"（20000ms 未返回）"——**模型只会说出它看到的东西**。
所以给模型人话、给运维日志，两端分开。

**配置全走环境变量，改机器不改代码。** 包括 DSH 路径、lark-cli 路径、状态目录。
写死绝对路径是部署杀手，而改了源码去部署，等于线上跑的是个跟仓库不一样的版本。

**飞书时间按 `+08:00` 显式解析。** 不取本机时区。本机是 UTC+8 所以一直对；
服务器默认 UTC，同一条消息会被解析成 8 小时前，水位线一比较把所有消息当旧的滤掉——
**部署上去看着完全正常，但永远收不到消息。**

**治理：模型判断风险，代码执行策略。** Router 给每个任务标 `read` / `write` / `irreversible`，
`src/policy.ts` 按档执行——**只有不可逆的才拦**（删东西、重置、强推）。什么都问等于没问，
最后人就会一路点"确认"，那时候确认就等于没有。不可逆的动作不派 Worker，先问一句，
回「确认」才动手；十分钟不回答就作废。

**对账：它是唯一能验证"它没骗你"的东西。** Worker 落地后取一次 `git status`，
和它自己的汇报对质。提示词能教它说"我没改任何文件"，只有工作区能证明这句话是真的。
两者矛盾时**标记为"疑似"**，不下判决——判错的代价由人担，那就该由人看。

## 已知没做到的

诚实清单，不是路线图：

- **只接了飞书一个源。** 换源只要实现 `TriggerSource`（`poll(): Trigger[]`）。
- **Thread 粒度是「群」不是「话题」。** 同一群里两个不相干的话题会互相带进上下文。
- **`recent` 历史只在内存**，重启即丢（它是"组装的方便"，不是事实）。
- **收尾会等出站队列把话发完。** 某条回话永远不返回，退出就会被拖住（systemd 有 30 秒兜底）。
- **没有大规模仓库索引 / GB 级检索。** 长内容 Spill 到文件，让 Worker 自己读。
- **一次最简往返约 14,470 tokens。** 所以"派很多 Worker"只在合成负载里成立，真实成本约束会改变调度策略。

## 这份代码想说明的一件事
架构文章里的判断，**没有一条能靠读文章验证**。182 秒和 3 秒的差别，
"Worker 什么都不说"和"Worker 说它没找到"的差别，都只有真跑起来才会出现。

所以这个仓库的价值不在它实现了什么，而在于它记录了**哪几条判断在真实环境里改过版**。
