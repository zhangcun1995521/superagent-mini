# 基准结果

`node src/harness.ts` 的实测输出（合成负载，本机 Windows / Node 24）。

## 负载与参数

- 20 个工作请求（分在 4 个 Thread，模拟同一 PR 的多轮）+ 200 条噪音
- 每个"工作" = 3 次模拟调用 × 200ms；Router 判断一次 = 200ms
- 事件按时间滴入，每条间隔 10ms

## 结果

```
方案               p50      p95      决策     模型调用      直通     token     总耗时
------------------------------------------------------------------------------------
A 单会话串行          827ms    839ms    220    220       0      267920    182.2s
B 双层+直通          633ms    3237ms   7      7         193    269953    5.5s
C 双层无直通          638ms    34506ms  200    200       0      273620    44.9s
```

## 三条结论

**① 订阅直通是这套架构里收益最大的一条，而且收益与"重复事件占比"成正比。**

B vs C：Router 决策 **200 → 7**（−96%），模型调用同样，总耗时 **44.9s → 5.5s**（8 倍）。
注意：文章消融实验里只说"决策 +30%"，我们是 28 倍——差别来自负载结构（我们是 200 条噪音 : 20 条工作）。
**所以不能引用文章的数字，只能引用自己负载下的数字。** 这是做基准第一条纪律。

**② 双层把 p50 打下来，但 p95 反而变差——这是真实取舍，不是 bug。**

A 的 p95（839ms）比 B（3237ms）好，因为单会话是"一件接一件、每件都准时开始"；
而 B 的 supervisor 是单线程：滴入间隔 + 每次 Router 调用（200ms）都在拖慢主循环，
晚到的请求要排队。**文章的判断是"Router 是全局序点，它慢全局慢"**，我们的数字正是这句话的证据。

要压 p95，三个方向（按代价排）：
1. 滴入更快 / 主循环更轻（我们的 10ms 滴入本身就吃掉了 4.4s）
2. Router 用更快模型（文章明说"Router 层任务常常没想象中复杂，轻量模型够用"）
3. 批处理调大（我们一次只处理一个 tick 的候选，真实系统可以让候选再积压一会儿）

**③ 直通让"连续性"和"省 token"同时成立，且没有牺牲完成时间。**

B 与 C 的 p50 几乎一样（633 vs 638），说明直通没有让单个任务变慢——
它只是让 Router 少做 193 次判断。这与文章的说法一致：直通不提高完成质量，省的是 Router 的开销。

## 两个"怎么测才有效"的坑（都是踩出来的）

1. **事件必须按时间滴入。** 第一版把 220 条事件塞进同一个 tick，B 和 C 的数字一模一样——
   因为"直通"的前提是 Worker 已经存在，而同一 tick 里的事件都早于 Worker 创建。
   **一个测不出差异的负载，会让人误以为架构没用。**
2. **到达时间要在事件进入系统那一刻记。** 第一版在启动前一次性写死，等于把排队等待算进了完成时间，
   而那段等待恰好是"系统忙不过来"的证据，该归到吞吐而不是延迟。

## 接真飞书之后撞到的九个坑

合成负载里全是假 Worker（`await sleep`），所以下面这些问题一个都不会暴露。
接上真飞书源 + 真 DSH 之后，它们接连出现——这一节比上面的数字更值钱。

**1. 同步调用把并发吃掉了。** `worker.step()` 原来走 `execFileSync`，
调它就是把整个进程钉住。日志实证：`+ Worker` 到下一行 `→` 之间 **182 秒**，
期间不轮询、不派活、不收新事件。改成 `execFile` + Promise 后，同一处间隔 **3 秒**。
"Worker 并发执行"这条主张，在同步 IO 下是假的。

**2. `execFile` 的 `timeout` 在 Windows 上不保证 promise 落地。** 它 kill 的是直接子进程；
`dsh` 会再派生子进程、持有管道，管道不关回调就一直不来。
实测：`timeout: 180000`，等了 6 分钟没回调，那个 Worker 的 promise 永远悬着，
`await Promise.all(pending)` 于是永久挂住。**必须有自己的一层看门狗**（`setTimeout` + `kill` + reject）。

**3. 空闲判定用错了口径。** 原来 `if (batch.length === 0)` 才进空闲分支。
但轮询源天生重复投递——每轮都把"最近 50 条"原样返回，去重之后 0 条新的，
`batch.length` 却一直是 1。于是空闲分支永远进不去：不 await Worker、不 sleep、不歇，
变成 4 秒一圈的**忙轮询**。更糟的是忙轮询每圈都在 `execFileSync` 里阻塞一下、
靠微任务续上，macrotask（定时器）被饿死——看门狗到点也没机会跑。
改法：用 `fresh`（过了去重的新事件数）判定空闲。
**教训："有没有新东西"必须用去重后的口径，不能把重复计数当成活动。**

**4. 空汇报被静默丢弃。** `if (text.length === 0) return` —— Worker 什么都没说，
这件事就消失了，用户永远等不到回应。空输出本身是一个结论（"它没干出东西"），必须回队。

**5. 一个 Worker 的死会带走 supervisor。** `.then` 没接 `.catch`，
dsh 超时/崩溃就变成无人处理的 rejection，最后在 `await Promise.all(pending)` 那里把常驻进程干掉。

**6. Worker 的插件集是继承来的，不是选出来的。** 原来 Worker 借用 `deepwork/.dsh-home-ui`，
那个 profile 挂了 7 个插件（ontology、external、session-query、lsp、test-runner、role、test-mode）。
于是**每个 Worker 启动时都是一个完整的企业原型**：它先去连飞书，撞上 Windows CNG 的 DPoP
签名失败（`key signer is unavailable`），一堆重试之后任务超时。同一个任务（读一个文件给一句结论）：

```
deepwork home  → 20 秒超时，一句结论都没有，日志全是飞书报错
干净的 home    → 7.8 秒，真的读了文件，结论是对的
```

**隔离不只是"独立会话"，还包括"独立能力集"。** 多带的每个插件都是一次它不该做的尝试，
以及一个它会踩到的坑。项目自己的 `.dsh-home` 由 DSH 首次运行时自动铺好，不用手工配。

**7. Worker 宁可耗死也不肯说"没找到"。** 回放的任务是"给 whyEmpty 加边界"，
而 `whyEmpty` 在那个工作目录里根本不存在（是另一个仓库的符号）。Worker 花 120 秒到处找、
最后超时。它的默认行为是继续猜，而不是报告"这里没有"。
现在任务后面固定跟一段执行纪律——找不到就停、说清查过哪里、**绝不为交差造一个替代实现**。
同一个不可能的任务：**120 秒超时 → 14.6 秒诚实报告**。

这条纪律必须写在指令里，因为"造一个替代实现"是最坏的失败形态：**它有产出，看起来像干成了。**

**8. 空闲就等于"停下等活干完"，以及回话把主循环堵住。** 两个问题同源：**常驻进程里有阻塞的地方**。

- 空闲分支 `await Promise.all(pending)`：看着是"别派出去就不管了"，实际是让 supervisor
  在 Worker 干活期间整个停住——一个 3 分钟的任务，3 分钟内不收任何事件。而那个担心是多余的：
  Worker 落地后汇报会变成一条 Trigger 进 `reportQueue`，下一轮自然就被捡起来。
- 飞书 IO 用 `execFileSync`：一次 3–6 秒，这期间进程是冻住的（不是慢，是冻住），
  定时器也不跑。改成 `execFile` + Promise，并照 `dsh` 那边的教训补一层看门狗
  （一次轮询挂住就是永久挂住，因为主循环 `await` 在它上面）。

**顺手撞出来的两件事：**

- **回话不能 fire-and-forget。** 一个 Thread 上会先后产生两句话：派活时的 ack 和 Worker
  落地后的结论。并发发出去顺序可能反——用户先看到结论再看到"收到"，比慢更难查。
  所以做出站队列：**串行发（保序），但不等在事件循环上（不阻塞）**。
  回话失败在队列里 catch 掉并记日志，一条失败不能断掉后面的。
- **不再 `await Promise.all(pending)` 之后，收尾条件要明说。** 原来那个 await 顺带起了一个作用：
  让出事件循环，使汇报有机会落地。现在收尾改成"没新事件 **且** 没有活在飞"才算跑完，
  否则测试用的 `maxTicks` 会在汇报落地前就结束。

**9. 我们把自己的实现细节讲给用户听。** 日志里原话：

```
→ 群: 派发的任务执行超时了（20000ms 未返回），「给 whyEmpty 加边界」暂未完成…
```

`20000ms` 和 worker 会话 id 都是实现细节。根因不在措辞，而在**输入**：
抛出来的错误原文是 `dsh headless 超时（20000ms）：worker-w-fb76ce2b-49dd219e`，
我们把它原样喂给 Router 让它"转述成一句话"——**模型只会说出它看到的东西**。

改法是把这一类问题拆成两层，分开修：

- **内容**：喂给模型的是人话（`执行没有完成：超时了。`），毫秒数和会话 id 进日志给运维。
- **形状**：`src/channel.ts` 保证出门那一句——剥内部信封（`[worker] w-ab12cd34: `）、
  压平空白、超过 400 字截断并把全文存成 `state/replies/*.md`。
  截断点落在换行或句号上，不把话切一半。

改完同一场景：

```
[supervisor] Worker w-fb76ce2b 失败（细节留在这里）：dsh headless 超时（20000ms）：worker-w-…
→ 群: whyEmpty 加边界的任务执行超时未完成，需要我重新安排一次吗？
```

会话里的两条消息：

```
收到，已安排给 whyEmpty 加边界处理。
whyEmpty 加边界的任务执行超时未完成，需要我重新安排一次吗？
```

**顺手抓到一个更隐蔽的错**：Worker 汇报被误判成 `dispatch` 时，兜底把 `decision.task`
当回话发了出去——**task 是"给执行者的指令"，不是"对用户说的话"**。
现在没有 reply 就老实说一句，不把指令念给用户。

## 真链路验证（不是基准，是"它到底转不转"）

```
15:08:09  + Worker w-fb76ce2b 起了一个 DSH 会话
15:08:11  → 群: 收到，已派给执行者给 whyEmpty 加边界处理。
15:08:33  → 群: 执行者已超时未完成 whyEmpty 的边界处理，需要重试或排查超时原因。
```

三句话说明三件事：轮询拿到了真消息（1 条，水位线之外）、Router 决定派活、
Worker 落地（这里是超时）后汇报**穿过** Router 变成第二句给用户的话。
中间那句是派活时的 ack，最后那句才是闭环——**用户能知道结果，包括失败的结果。**

异步化之后同样的链路（ack 和结论相隔 28 秒，顺序没乱）：

```
15:44:37  启动。群 oc_...，轮询 5000ms
15:44:49  + Worker w-fb76ce2b 起了一个 DSH 会话
15:44:52  → 群: 收到，已派给执行者处理。
15:45:20  → 群: 派发的任务执行超时了（20000ms 未返回），「给 whyEmpty 加边界」暂未完成…
```

复现（用群里一条真实历史消息回放，不碰历史）：

```bash
SAM_CHAT_ID=oc_xxx FEISHU_SINCE=2026-10-29T14:57:00.000Z \
  DSH_WORKER_TIMEOUT_MS=20000 node src/run.ts
```

## 治理层：怎么验证它真的拦得住

治理最怕的是"写了但没生效"。所以它的验证方式和前面那些坑不同——**不是测数字，是反向证明**：

```
把 policy.gate() 改成永远返回 "go"（等于没有门禁）
  → 两条审批测试立刻失败（不可逆的动作被直接派了 Worker）
把 gate() 改回来
  → 44 条全绿
```

同理，对账那条测试是这么写的：Worker 自称"我没有改任何文件"，而注入的工作区快照说
`src/filter.ts` 变了——断言证据里必须出现 `suspectContradiction`。

**做对账时候撞到的：** 对账函数第一版写成"git 失败就返回空数组"。跑真链路时看到：

```
[15:55:07] 对账失败（当作没有改动）：Command failed: git status --porcelain=v1
```

这行日志救了这条设计——因为 superagent-mini 当时还不是 git 仓库。如果当时悄悄返回空数组，
**"真的没改动"和"根本没查到"会长得一模一样**，而这正是治理层最不该犯的错。
现在失败会打原因，空结果不再冒充"确认没改"。

## 已知没做到的（留给下一步）

- **Worker 在 agent 自己的目录里干活**，还没有"这个任务去哪个仓库"的概念。
  对账因此只能盯一个目录，而且多任务并发时会看到彼此的改动（宁可多记，不可漏记）。
- **出站队列没有持久化，也不重试**：进程死了队列就没了。官方原型的 `outbox` 有回执落盘
  和退避重试——见 `docs/COMPARE.md` 第 2 节，这是读完他们代码后我认下的第一条要补的。
- **Thread 粒度是「群」不是「话题」**：同一群里两个不相干的话题会互相带进上下文。
- `recent` 历史只在内存，重启即丢（它是"组装的方便"，不是事实）。
- **收尾会等出站队列发完**：如果某条回话永远不返回，退出会被拖住（systemd 有 30 秒兜底）。
- 没有大规模仓库索引 / GB 级检索；长内容 Spill 到文件，Worker 自己读。

## 复现

```bash
node src/harness.ts     # 约 4 分钟（A 方案是串行，占 182 秒）
```

要快些可以改 `JOBS` / `NOISE` / `CALL_MS` 三个常量；结论方向不会变，比值会变。
